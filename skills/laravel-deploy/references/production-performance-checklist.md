# Production performance checklist

Use this template to establish a baseline, find the dominant costs, and verify fixes against the same workload. Record the evidence link and owner next to each check as you run it. For an inapplicable check, record the reason and leave its box unchecked.

## Scope and baseline

This is a reference application profile. The examples use PHP 8.4 with PHP-FPM, Laravel 13, PostgreSQL 17, React 19, Tailwind 4, and Vite 8 on EC2. No production inventory, traffic distribution, or measurements were supplied. Check the deployed versions and lockfiles first. Use the matching manual if they differ. Redis, PgBouncer, ALB, CDN, Horizon, Octane, and HLS checks apply only under their stated conditions. On a Sail project, use the project’s Sail wrapper for staging Artisan commands.

- Record the release SHA, runtime and package versions, region, origin and edge topology, instance type, dataset cardinality, persona, and test accounts. Pick a public landing page, an authenticated journey with a repeatable interaction, and a high-cost read endpoint. Use an authorized synthetic account and a representative, sanitized staging dataset.
- Freeze the route and inputs, data snapshot, offered arrival rate and concurrency limits, test duration, region, browser build, viewport and device profile, and network/CPU shaping. Label browser cache, CDN cache, and application cache states individually. Compare cold-to-cold and warm-to-warm. Warm up before steady-state load and report cold starts separately. Run controlled load and intrusive profiling in staging, including any SQL execution plans for writes.
- Capture production RUM or CrUX p75 by mobile and desktop when samples support it. Prefer route-level RUM and label CrUX origin-level data when URL-level data is unavailable. Use comparable cohorts and windows. For lab diagnosis, keep at least five runs per browser scenario and report the median and spread. Use interaction traces for responsiveness and label Lighthouse Total Blocking Time (TBT) as a lab proxy. Break LCP into TTFB, resource load delay, download duration, and render delay. [Core Web Vitals](https://web.dev/articles/vitals) · [Navigation TTFB](https://web.dev/articles/ttfb) · [LCP phases](https://web.dev/articles/optimize-lcp)
- For each candidate, record the baseline and candidate values in the same units, sample size, artifact link, and decision. Compare latency at the same offered load and report achieved throughput and concurrency. Record error rate, saturation, and cost per request or job for capacity changes.

### Starter budgets

These are provisional, except the published Core Web Vitals thresholds. Apply the byte budgets to a cold-cache first view, from navigation through the journey's first-view-ready marker plus two seconds. Sum encoded response **body** bytes, deduplicated by actual network response, including third-party resources. Use Resource Timing `encodedBodySize` where available and DevTools response data for cross-origin resources whose sizes are hidden. Separate CDN encoding from the build tool's compressed size estimates. [Encoded response sizes](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming/encodedBodySize)

| Metric | Starting limit | Scope |
| --- | ---: | --- |
| LCP / INP / CLS | ≤ 2.5 s / ≤ 200 ms / ≤ 0.1 | Field p75 per route and device class, if available |
| Navigation TTFB | ≤ 800 ms | Field p75 for document navigations, including connection setup |
| Initial JavaScript | ≤ 200 KiB | Encoded JS bodies loaded by each critical route |
| Initial CSS | ≤ 35 KiB | Encoded CSS bodies loaded by each critical route |
| Critical images, video, and fonts | ≤ 300 KiB | Combined encoded bodies fetched before first-view-ready on the mobile scenario |
| API p95 | ≤ 300 ms hot read, ≤ 600 ms for the database-heavy read | Server ingress to response completion at representative peak arrival rate, segmented by endpoint and status |
| SQL queries per request | ≤ 10 | First page of the hot list at target cardinality, including framework queries |
| Cumulative database time p95 | ≤ 100 ms | Per-request sum of application-observed SQL durations on the hot read at peak load |
| Queue wait p95 | ≤ 5 s | Time from eligible to first execution for the user-facing lane at peak load. Split retries and intentional delays out. |

Calibrate each provisional limit against representative baseline distributions, user-facing targets, and capacity headroom. If the baseline exceeds a target, agree on a staged improvement and set the initial CI gate above normal test variability while blocking regressions. Keep cold and warm budgets distinct where they differ materially.

### Priority and change verification

High covers critical journey latency or peak capacity. Medium covers narrower impact. Low covers incremental gains. Effort includes the typical fix and verification. S is up to half a day, M is up to two days, and L is more than two days or cross-team work.

For a capacity, cache, or persistent-worker change, record the previous config or release, named before-and-after metrics, canary scope, and rollback owner. **R** means revert to that prior version if a check's SLO or capacity guard is breached in two consecutive five-minute windows with at least 100 requests per window or 30 jobs per lane per window. When no SLO exists, use a provisional regression guard of more than 10% relative worsening on the named latency, queue, or resource metric at matched load. Adapt those windows to real traffic before the canary. Roll back immediately for cross-user cache responses, invalid application state, or OOM/restart loops that affect service.

- [ ] **BASE-01 Save repeatable journey baselines** — **Priority** High · **Effort** S · **Verify** Staging, run the fixed public, authenticated, and database-heavy scenarios and save manifests with HARs, traces, and load results. · **Pass** A teammate can repeat each run with the same dataset, cache states, device/network, and load.
- [ ] **BASE-02 Record field distributions by device** — **Priority** High · **Effort** S · **Verify** Production metrics, export p75 LCP, INP, CLS, and navigation TTFB for each supported route/device cohort. · **Pass** Each threshold has an observed value and sample window, or a recorded data gap.
- [ ] **BASE-03 Identify the dominant cost of each slow journey** — **Priority** High · **Effort** S · **Verify** Staging, align the browser waterfall and interaction trace with application and SQL spans under the baseline workload. · **Pass** The slow phase, attributed resource or code path, and supporting evidence are recorded.
- [ ] **BASE-04 Assign provisional budgets to the three journeys** — **Priority** High · **Effort** S · **Verify** CI or staging, populate the budget table from route bytes, request timing, query traces, and queue metrics. · **Pass** Every applicable budget has a unit, workload, baseline, and owner.

## Laravel and PHP

- [ ] **PHP-01 Optimize Composer's production autoloader** — **Priority** High · **Effort** S · **Verify** CI, use `composer install --no-dev --optimize-autoloader --no-interaction` in the production artifact job from the lockfile. Inspect the install log and smoke boot the artifact. · **Pass** Composer generates the optimized classmap and the artifact resolves application and production package classes.
- [ ] **PHP-02 Generate Laravel caches for the target environment** — **Priority** High · **Effort** S · **Verify** Release build or staging, run `php artisan optimize` with target configuration and inspect the config, event, route, and view task output. Build environment-dependent config after target settings are supplied. · **Pass** All four cache tasks succeed for the promoted release.
- [ ] **PHP-03 Smoke test the cached release** — **Priority** High · **Effort** S · **Verify** Staging and production canary, request the configured health endpoint, one public page, and one authenticated flow and exercise one expected event/listener using an approved synthetic action. · **Pass** Statuses, rendered content, session continuity, and the listener result match the release expectations. Compare p95 and errors before/after. Roll back on a failed smoke or R.
- [ ] **PHP-04 Verify OPcache in the serving pool** — **Priority** High · **Effort** S · **Verify** Read-only production inspection, collect `opcache_get_status(false)` through an existing internal FPM diagnostic. Compare post-warmup hit rate, key/memory headroom, and restart deltas by pool. · **Pass** OPcache is enabled in FPM, counters stay below capacity, and no OOM/hash restart occurs during the window. Compare API p95 and restart counters before/after changes. Roll back on R or serving stale code.
- [ ] **PHP-05 Keep query count flat as list size grows** — **Priority** High · **Effort** S · **Verify** Staging, use Laravel `DB::listen` or APM SQL spans with cold application caches at small and large page cardinalities. Identify repeated relationship SQL. · **Pass** Query count stays within budget without a per-parent slope and eager loading only fetches required relations and columns.
- [ ] **PHP-06 Keep queue retries bounded** — **Priority** High · **Effort** S · **Verify** Staging, inspect the effective tries, backoff, timeout and reservation/visibility settings and inject a transient job failure. For drivers using `retry_after`, verify the worker timeout is shorter. · **Pass** Retries are bounded and observable, terminal failures are visible, and a running job is never picked up again because its reservation expires first.
- [ ] **PHP-07 Bound read pagination** — **Priority** High · **Effort** M · **Verify** Staging, test maximum requested page size and late-page behavior in the hot list. Compare offset, simple, or cursor pagination where UI and ordered index allow. · **Pass** The server caps the page size, ordering is deterministic, and late-page latency stays within the route budget.
- [ ] **PHP-08 Keep deferrable work off the request path** — **Priority** High · **Effort** M · **Verify** Staging, trace the request and its test job across dispatch, commit, and completion. Exercise retry with a synthetic job. · **Pass** The request returns within budget, the intended work runs once in effect after the required commit, and retries preserve correctness.
- [ ] **PHP-09 Keep queue wait within budget at peak** — **Priority** High · **Effort** M · **Verify** Production metrics, chart eligible-to-start p95, ready backlog, running workers, and database connections by lane. If Horizon manages Redis queues, compare its per-queue wait/throughput metrics. · **Pass** Wait meets budget and backlog drains at the target rate with worker and DB headroom. Compare wait and connections before/after changes. Roll back on R.
- [ ] **PHP-10 Verify Redis sessions across replicas** — **Priority** High · **Effort** M · **Verify** If Redis stores sessions, route an authenticated synthetic journey across two staging targets with the same release and environment config. · **Pass** The effective driver, connection, prefix and session lifetime match the design and the session survives the target switch. Compare session errors and Redis p95 before/after. Roll back on auth regression or R.
- [ ] **PHP-11 Verify Octane request-state isolation** — **Priority** High · **Effort** M · **Verify** If Octane is used, alternate two staging users/tenants on persistent workers and inspect captured request state, scoped services, and singleton dependencies. · **Pass** Neither user sees stale request data or the other's state. Roll back the release immediately on a leak.
- [ ] **PHP-12 Verify Redis cache wiring** — **Priority** Medium · **Effort** S · **Verify** If Redis backs the cache, use read-only production inspection of effective cache store/connection/prefix and isolated staging cache read/write and expiry tests. · **Pass** The intended store and TTL are applied, environments are isolated, and Redis p95 and evictions remain within budget. Compare before/after. Roll back on R or invalid cache results.
- [ ] **PHP-13 Measure logging and telemetry overhead** — **Priority** Medium · **Effort** S · **Verify** Staging, compare current and reduced log/trace sampling with the same workload, including a slow sink. · **Pass** Request p95 and errors stay within budget and the slow and failing paths remain observable. Revert sampling changes that break observability or R.
- [ ] **PHP-14 Scope debug collectors** — **Priority** Medium · **Effort** S · **Verify** If Debugbar or Telescope is installed, inspect deployed configuration and replay normal and exceptional requests in staging. Check production authorization, filtering/sampling, and retention where collection is enabled. · **Pass** Normal production responses carry no debug UI. Any enabled production collector only records intended events with bounded retention and access.
- [ ] **PHP-15 Limit API responses to fields the client uses** — **Priority** Medium · **Effort** S · **Verify** Staging, compare the response schema, encoded bytes, and browser consumers for the journey. · **Pass** The API serves the fields needed for the view within its p95 budget. The mounted-row count is recorded separately in FE-04.
- [ ] **PHP-16 Bound large-write batches** — **Priority** Medium · **Effort** M · **Verify** Staging, compare per-row writes with chunked bulk insert/upsert on equivalent data. Inspect transaction duration and the required model events, timestamps, and conflict behavior. · **Pass** Batch size is bounded and results, side effects, and peak lock duration meet the workflow's requirements.
- [ ] **PHP-17 Bound Octane worker memory** — **Priority** Medium · **Effort** L · **Verify** If Octane is evaluated or used, run a staging soak against FPM or the prior Octane configuration. Track throughput, p95, RSS over worker lifetime, recycling, and errors. · **Pass** The chosen configuration meets its latency/throughput target and RSS stabilizes or is bounded by recycling. Roll back on unbounded growth, restart loops, or R.
- [ ] **PHP-18 Require an A/B result before adopting JIT** — **Priority** Low · **Effort** M · **Verify** If evaluating JIT on a CPU-bound workload, compare serving FPM runtimes with JIT off/on under the same load. Inspect actual JIT state and memory after warmup. PHP 8.4 changed the `opcache.jit` default to `disable`. · **Pass** The candidate repeatably improves throughput or CPU/request at equivalent p95 and memory budgets. Keep the prior config if it fails or roll back on R.

## PostgreSQL

- [ ] **PG-01 Rank queries by incremental total time** — **Priority** High · **Effort** S · **Verify** Read-only production inspection, if `pg_stat_statements` is available, take two snapshots of `dbid, userid, queryid, calls, total_exec_time` and rank deltas across the same peak window. Check the reset time and representative sample. · **Pass** High-total-cost fingerprints have owners and traced endpoints. When the extension is absent, record the gap and use APM or existing logs to rank first.
- [ ] **PG-02 Find the high-latency query tail** — **Priority** High · **Effort** S · **Verify** Production metrics or staging, inspect existing duration logs or APM distributions grouped by fingerprint. If enabling sampled slow-query logs, set a bounded threshold and review data retention. · **Pass** Slow classes have elapsed-time distributions, call volume, and workload context. Record log volume and request p95 before/after any logging change and revert on R.
- [ ] **PG-03 Capture a representative execution plan** — **Priority** High · **Effort** S · **Verify** Staging, use `EXPLAIN (ANALYZE, BUFFERS)` on the real query shape with representative parameters and data. Commands with `ANALYZE` execute the statement. Run write plans only in disposable staging data and account for trigger side effects. · **Pass** The plan, actual time, buffer work, parameters' selectivity, and the expensive node are recorded.
- [ ] **PG-04 Explain critical-path lock waits** — **Priority** High · **Effort** S · **Verify** Read-only production inspection, sample `pg_stat_activity` for `wait_event_type = 'Lock'` and use `pg_blocking_pids(pid)` with transaction ages to identify long blockers. · **Pass** No unexplained recurring lock wait breaches the affected endpoint's budget.
- [ ] **PG-05 Keep table statistics and vacuum current** — **Priority** High · **Effort** M · **Verify** Read-only production inspection, inspect `pg_stat_user_tables` for `n_dead_tup`, `n_mod_since_analyze`, `last_autovacuum`, and `last_autoanalyze`. Compare trends with table churn and long transactions. · **Pass** Hot tables keep pace with churn and have adequate stats. Compare dead tuples, vacuum I/O, and query p95 before/after tuning. Roll back on R.
- [ ] **PG-06 Resolve material row-estimate errors** — **Priority** High · **Effort** M · **Verify** Staging, compare estimated and actual rows per loop at the expensive plan nodes and check `pg_stats` and fresh statistics. Start investigating around a 10× error when it changes plan choice. · **Pass** Material errors are explained or corrected and the candidate plan improves observed time or buffer work across common parameter sets.
- [ ] **PG-07 Match indexes to the actual workload** — **Priority** High · **Effort** M · **Verify** Staging, compare plans for actual filters, join keys, sort order and selectivity before/after the index. Test write overhead and index size with the same dataset. · **Pass** The index lowers hot-query p95 or buffer work without exceeding write-latency and storage budgets. Roll back the index change on R.
- [ ] **PG-08 Validate PgBouncer before changing pool mode** — **Priority** High · **Effort** L · **Verify** If PgBouncer is used or connection pressure warrants it, compare `SHOW POOLS` and `SHOW STATS` with PostgreSQL connection headroom and application p95. In staging, test transaction pooling compatibility with session state, temporary objects, and prepared statements on the installed PgBouncer version. · **Pass** Connection waits improve within budget and app semantics remain correct. Roll back on compatibility failures or R applied to pool wait, connections, or request p95.
- [ ] **PG-09 Account for temporary-file spills** — **Priority** Medium · **Effort** S · **Verify** Read-only production inspection, compare `pg_stat_database.temp_files` and `temp_bytes` deltas, correlating with query statistics or `log_temp_files` where enabled. Reproduce in staging plans. · **Pass** Material spills on hot queries are traced to a plan node and remain within the latency and disk-I/O budget.
- [ ] **PG-10 Budget PostgreSQL memory for peak concurrency** — **Priority** Medium · **Effort** M · **Verify** Read-only production inspection, use `SHOW shared_buffers`, `SHOW work_mem`, and `SHOW effective_cache_size`. In staging, test total memory, spills, and p95 under concurrent plans. Model `work_mem` per operation and parallel worker. Treat `effective_cache_size` as a planner estimate. · **Pass** The configuration leaves host headroom and achieves the intended spill/latency result under peak load. Compare before/after and revert on R or OOM.

## Delivery and caching

For repeat GET checks, use `curl -sS -D - -o /dev/null '<url>'` from the measured region. Use actual test account sessions for personalized flows and redact credentials from artifacts. Match representation, encoding, effective cache key, and POP between comparisons.

- [ ] **EDGE-01 Keep personalized responses private to the requester** — **Priority** High · **Effort** S · **Verify** Staging or authorized production canary, request the same URL as a guest and as two synthetic users. Inspect `Cache-Control`, `Vary`, edge cache status, and expected response markers. · **Pass** No user's response is reused for another user or guest. Compare origin load and p95 before/after the policy change. Roll back or disable the shared rule immediately on cross-user reuse, or on R.
- [ ] **EDGE-02 Cache content-hashed assets across repeat visits** — **Priority** High · **Effort** S · **Verify** Production read-only, GET a manifest-referenced hashed asset and inspect its cache headers, then confirm a changed build emits a new URL for changed bytes. · **Pass** Hashed assets have long-lived `public, max-age=31536000, immutable` or equivalent policy, with no immutable rule on stable URLs.
