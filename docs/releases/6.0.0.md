# Laravel Guild 6.0.0

## What’s new

Laravel Guild now treats path ownership as an executable delivery boundary.
Every stage that may write must claim at least one project-relative path before
the plan is persisted. Read-only agents may remain pathless because their
harness policy denies mutation.

When a stage reports completion, each `DID` path must be the owned path itself
or a file nested beneath it. A report that claims an output elsewhere is
rejected without changing delivery state. This complements the existing
parallel-collision check: ownership now controls both dispatch and completion
evidence.

The README also includes a new engineering-loop diagram showing how requests
move through planning, bounded execution, verification, review feedback, and
approved learning.

## Breaking changes

The comma-delimited `plan --stage` form has been removed because it cannot
declare ownership. Replace it with a typed stage record:

```sh
python3 scripts/guild-kernel/guild.py plan \
  --root . \
  --name tags \
  --done-when "POST /api/tags returns 201" \
  --stage-json '{"id":"backend","agent":"backend-developer","role":"writer","success_criteria":["Tag endpoint returns 201"],"depends_on":[],"owned_paths":["app/Http/Controllers","routes/api.php"]}'
```

Every `--stage-json` object must include `owned_paths`. Use a nonempty array for
`task-owned` and `docs-only` agents. Use `[]` only when the selected agent has a
`deny` mutation policy, such as `performance-engineer` or `security-engineer`.

Existing saved deliveries remain readable. Complete or archive a historical
delivery with empty writer ownership, then start new work under a typed v6 plan.

## Verification

- Kernel tests cover required ownership, read-only exceptions, invalid path
  shapes, nested in-scope outputs, and rejected out-of-scope outputs.
- CLI tests cover the typed ownership field and the legacy-form migration error.
- Harness, guardrail, generated-target, inventory, and manifest checks remain
  release gates.
