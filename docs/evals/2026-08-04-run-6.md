## Findings

### 1. `n-plus-one`'s 3.1× slowdown is empirical verification, not degradation — DIAGNOSED

**Corrected twice, so read this version and ignore the earlier framing.** This
finding first said the case was "creeping badly" and was "the thing to explain,
not absorb", then proposed per-agent `effort` as its lever. Both were wrong. A
follow-up run with `KEEP_TRANSCRIPT=1` (226s, $1.36, 4/4 checks — same shape as
run 6's 302s, so the number is stable, not an outlier) shows what the time buys.

**The 16 Bash calls, in order:** seven of reconnaissance (`ls`, `grep routes/`,
`find app resources database tests`, `cat phpunit.xml composer.json`, probe for
`vendor/`, check `php -v` / `composer --version` / PDO-SQLite, `cat .gitignore`),
then **`composer update`** to install dependencies, then `bootstrap/providers`
inspection — and then **six runs of Pest against three temporary probe tests it
wrote itself** (`TmpNPlusOneProbeTest`, `TmpFixProbeTest`, `TmpSemanticsProbeTest`),
before deleting all three and leaving the tree clean.

So the case is not flailing and it is not over-thinking. **It installs the app and
then proves the N+1 empirically** — demonstrating the query explosion, validating
the candidate fix, and checking the fix preserves semantics — instead of reading
the Blade template and reporting a diagnosis. Run 3's 96s was a static read. The
extra ~200s is the cost of executable evidence, and it shows in the score: 4/4
checks and the judge's only 5/5 with no criticism.

**Why the v1.16.0 static-mode lever did not prevent it.** That rule — one `vendor/`
probe, then declare static mode rather than retry-flailing — lives in *agent
bodies* (`performance-engineer`, `qa-engineer`, and nine others) and in the
`eloquent-performance` skill. This case never enters one: `/audit-n-plus-one` runs
**entirely on the main thread** (board feed empty in run 6 and in the diagnostic
run alike, despite the command being granted the `Agent` tool). No agent body
governs the main thread, so no static-mode rule reaches it.

**This is a trade-off to choose, not a bug to fix**, and the ceiling raised to 400s
already accommodates it:

- **(a) Accept it.** Empirical verification is worth ~3× the wall clock on an audit
  command. Stop calling it a regression; the creep narrative was wrong.
- **(b) Delegate to `performance-engineer`.** The command already holds the `Agent`
  tool, and that body *does* carry the static-mode rule — faster and read-only, at
  the price of the executable proof.
- **(c) Put a verification-budget rule where the main thread can see it** — the
  command body itself, since agent bodies structurally cannot reach it.

**Recommended: (a).** The evidence says the slower run is the better run. Worth
knowing (b) exists as a deliberate lever now that it is costed, rather than
discovering it as a mystery again in run 8.

### 2. The judge earned its keep on its first outing

Two cases scored 4/5. Both criticisms are legitimate, and neither is something the
regex answer key could have raised:

- **`action`** — *"app/Actions/ is untracked and its body is absent from the diff,
  so the mail fan-out, site_stats increment and Log::info re-implementations are
  asserted by the transcript, not shown."* Real, and the defect is in the
  **evidence artifact, not the answer key**. (An earlier draft of this doc blamed
  `checks_action`; that was wrong. The checks read the filesystem directly — `find`,
  `grep`, and `git status --porcelain`, which *does* list untracked files — so they
  are not blind to a new file.) What is blind is `<case>.diff.patch`, built with
  plain `git diff`, which **omits untracked files entirely**. That artifact is
  exactly what the judge is given as evidence, so on a case whose whole job is
  *creating* a class, the judge could confirm the file existed but never see a line
  of its body. Verified directly: a new untracked file contributes 0 lines to
  `git diff`; after `git add -N` both the path and its `Mail::to` body appear.
  **Fixed** — `run_case` now records intent-to-add before diffing, after the checks
  and after `status.txt`, so no verdict and no other artifact changes.
- **`tests`** — *"Authz assertion exists but is `->todo()`, so it never executes —
  the IDOR is documented rather than demonstrated, and CI stays green with the
  flaw live."* This looked like a pure judgment call against a deliberate v1.24.0
  decision. It turned out to expose a **contradiction inside `qa-engineer`'s own
  body**: the authorization rule prescribed `->todo()`, while the anti-patterns
  section three paragraphs later demanded that same test "asserts the secure
  outcome **and fails loudly**". A `->todo()` does not fail loudly, so the body
  told the agent two incompatible things and the judge caught the consequence.
  **Resolved in v1.35.0**, keeping v1.24.0's actual point (assert the *secure*
  outcome, never pin the hole as expected behaviour) and making the run/don't-run
  decision explicit instead of defaulted: leave it failing when the flaw is
  in-scope work, or mark it incomplete when it is pre-existing and out of scope —
  a red pipeline you did not cause blocks everyone else too. Either way FLAGS must
  name the endpoint, say the vulnerability is live, and say the suite will not
  catch it. "Loudly" is now defined as *the human hears it*, which a marked test
  plus a FLAGS entry satisfies and a marked test alone does not.

The judge stayed advisory throughout and changed no verdict, as designed.

### 3. The cost instrument had two defects that only real data could expose

Both found by this run, both fixed:

- **Dated model ids were unpriced.** Transcripts report
  `claude-haiku-4-5-20251001`; the rate table and agent frontmatter use the alias
  `claude-haiku-4-5`. The dated id missed the table, fell through to the default
  Opus rate, and priced `scrum-master` **5× too high**. The rate-table
  reconciliation caught it rather than reporting a wrong number quietly: billed
  $0.622 against a repriced floor of $0.690, with an implied cache-write
  multiplier of 0.99 — below the 1.25 tier floor, i.e. arithmetically impossible.
  Fixed by resolving a trailing `-YYYYMMDD`, plus a test asserting every model any
  agent pins is priceable.
- **A phantom `unknown-agent` lane.** Three cases spawned no subagent at all
  (empty board feed) yet reported an `unknown-agent`, which the harness announced
  as *"launched but unmeasured (async?)"* — inventing a lane in the one report
  meant to be authoritative about lanes. Cause: any `task_started` line carrying a
  `tool_use_id` was treated as an agent launch, with a fallback name. A
  `task_started` without a `subagent_type` is not an agent launch and is now
  skipped.

### 4. Token totals are >99% cache reads, so tokens alone cannot ratchet cost

Every case: n-plus-one 3,666,860 cache of 3,669,451 total; the others 100.0% to
one decimal. Cache reads bill at 0.1× input, so **`max_tokens` measures context
volume × turns, not spend.** A token-only ceiling would have been close to
useless as a cost guard — it would move with prompt size and turn count while
missing a model-mix regression entirely (a sonnet → opus re-tier keeps tokens flat
and triples the bill).

`baseline.json` therefore now carries **three** ceilings — `max_seconds`,
`max_tokens`, `max_usd` — with the division of labour written down: dollars speak
for cost, tokens for work volume, and the rate-table reconciliation distinguishes
a price change from a regression.

### 5. `policy` and `action` are bimodal, and run 6 swapped their modes

Run 5 delegated `policy` (994s) and fast-pathed `action` (420s). Run 6 did the
exact opposite: `policy` finished in **381s with no delegation at all**, `action`
took **1217s across four agents**. Both breached or undershot ceilings set from
the other mode.

This is the coordinator's fast path working as designed, but it makes those two
cases' ceilings mode-dependent. Ceilings are seeded from run 6 **without**
inflating them to cover both modes, and `baseline.json` records the caveat: on a
REGRESSED reading for either case, check the agent list in `<case>.cost.json` for
delegation before calling it a regression.

### 6. The tranche's over-trigger risk did not materialise — because item 2 never fired at all

The held tranche's item 1 (`NOT-CHECKED` escalation) carried a stated risk: a
specialist dumping adjacent surfaces into `NOT-CHECKED` could stall a lane on
checkpoint prompts. **No case produced a checkpoint prompt or a stalled lane**,
and no case exceeded its stage budget.

That is a weak negative, though: only `action` and `tests` delegated at all, and
neither hit a checkpoint category. `policy` — the case most likely to trigger one,
and the case that delegated in run 5 — did not delegate this time. **The
escalation path is still effectively unexercised.** Do not read run 6 as
clearing it.

**And the stage-budget half of this finding was vacuous.** "No case exceeded its
stage budget" was true only because **no case was ever bound by one.** The opt-in
`feature` case (added in v1.34.0, first run 2026-08-04: 1456s, $6.55, 11.2M
tokens, 5/6) proved it: the single failing check was the stage-budget assertion,
and the rubric judge independently reached the same conclusion while *disagreeing
with the regex verdict* — *"the stage table appears only as a closing summary —
evidence shows 6 owned stages but no up-front stage count or stated observable end
condition before the agents spent tokens."*

The cause is structural, and it is the second confirmed instance of the same gap
as finding 1: **the tranche's rule lived only in `agents/delivery-coordinator.md`,
and `/make-feature` is driven by the main thread — `delivery-coordinator` is never
spawned** (the board feed for that run names database-developer,
backend-developer, qa-engineer and tech-lead, and no coordinator). A rule written
into an agent body cannot govern work the main thread does inline through a
command. This is precisely the v1.24.0 finding recurring: that release moved the
`NOT-CHECKED` contract into the 9 commands' shared `Interface` block because a
coordinator-only version was invisible to headless runs.

**Fixed the same way in v1.36.0** — the shared `Interface` block now requires the
board's header to state the stage count and the observable completion condition
up front, byte-identically across all 9 pipeline commands, with a ratchet.

### 7. The answer key failed a correct run, and the judge caught it — the audit's antipattern, live

The 2026-08-05 `policy` run scored **2/3 on the regex key while the rubric judge
scored it 5/5 and disagreed with the verdict.** The judge was right.

The failing check was `check_log 'update'` — a grep for one word in the final
answer. The run closed the hole properly: `PostPolicy@update` returns
`$user->id === $post->user_id`, and the update path is guarded by
`UpdatePostRequest::authorize()` calling
`$this->user()?->can('update', $this->route('post'))`, with a feature test
asserting a non-owner PUT gets 403 and the post's fields stay unchanged. It simply
never used the literal word "update" in its closing prose — zero occurrences in
the log — so a wording accident scored as a quality failure.

This is the **exact antipattern the 2026-07-29 literature audit named, citing this
exact check**: exact-match grep scoring of nondeterministic output. v1.26.0's
response was the rubric judge as a second opinion, and it worked precisely as
designed here — its first catch of a *false negative*, after run 6's two catches
of things the key over-credited. The judge has now disagreed with the key twice,
and been right both times.

**Fixed at the artifact level** (v1.37.0): `check_update_guarded` inspects the
code rather than the prose, accepting either idiomatic placement — the guard
inline in the controller's `update()`, or in the `authorize()` of the Form Request
that `update()` type-hints. Verified against four scenarios: both idioms pass, the
planted flaw fails, and — the one worth having — a Form Request whose `authorize()`
just `return true` also fails, because a guard that authorizes everything is not a
guard.

### 8. `policy`'s two modes differ by 3.3× in cost, which makes the mode matter more than the ceiling

Same case, same prompt: 381s / $2.19 / 4.4M tokens undelegated (run 6), and
1560s / $7.18 / 11.4M tokens across four agents (2026-08-05). All three of its
run-6 ceilings read REGRESSED on the delegating run — and `baseline.json`'s own
`_bimodal_cases` note is what made that legible rather than alarming: check the
agent list before calling it a regression. It did its job.

Both bimodal cases are now seeded to cover the **delegating** mode, so an
undelegated run reads comfortably inside and the agent list — not the ceiling —
tells you which mode ran.
