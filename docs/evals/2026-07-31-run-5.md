## Findings

### 1. The per-case event feeds are polluted by committed fixture state — fix this first

`tests/fixture-app/.claude/agents-board.jsonl` is **committed**, holding stale
telemetry from two 2026-07-30 sessions (sids `102ca04e`, `6a368588`, tasks
"One-sentence test priority" and "Run single mkdir command"). The harness does
`cp -R "$FIXTURE/." "$WORK/"`, so **every case's feed begins with those lines**.

Read naively, this run's telemetry says every case — including `hygiene`, which
runs scrum-master, and `n-plus-one`, which runs performance-engineer — ran two
`qa-engineer` stages of exactly 3000ms and 5000ms. All five cases report the same
two, because it is the same committed file five times.

It is only detectable by noticing that the durations are suspiciously round and
identical across unrelated cases, then filtering by `sid`. Every number in this
document is computed with the two seeded sids excluded.

**Fix:** the fixture should not ship a board feed at all — it is session
telemetry, not fixture data. Either drop it from `tests/fixture-app/` (it is
gitignored at the repo root, so nothing else depends on it) or have the harness
truncate it after the copy. Until then, no per-agent analysis of any past run is
trustworthy without the `sid` filter.

### 2. `policy` regressed to exactly 994s again, and security-engineer is the driver

994s in run 4, 994s here — the same number twice, which is worth a raised eyebrow
but the sub-stage breakdown is now visible and it is real work:

| lane | duration |
| --- | --- |
| `backend-developer` | 103s |
| `qa-engineer` | 158s |
| `security-engineer` | **526s** |

787s of the 994s is subagent time and two thirds of that is one lane. This is a
*different* hog from the one 1.16.0's scope rule targeted (qa-engineer, then
448s). The case passes all three checks, so this is cost, not correctness.

Nothing has been changed for it. Before tuning, the obvious question is whether
526s of security review on a single-model Policy is the intended shape of
`/add-policy` — the command routes to security-engineer by design, and this may
simply be what that costs.

### 3. `composer install` cannot be attributed to worktrees — the run-4 lever was aimed at the wrong thing

Run 4 concluded that "two cases burned a stage on `composer install`" and that
`isolation: worktree` was the cause, because a worktree checks out tracked files
only. v1.24.0 removed the isolation. This run shows the reasoning does not hold:

**the eval fixture never has `vendor/` in the first place.** `install.sh` installs
the *pack* into the workdir (17 agents, 13 commands, hooks) — it installs no PHP
dependencies, and `vendor/` is not committed to `tests/fixture-app/`. So an agent
that needs to execute anything must install dependencies regardless of whether it
is in a worktree or the main tree.

What actually changed is better than the checklist item asked for: **no subagent
burned a stage on it.** The single occurrence is `n-plus-one` running it on the
**main thread**, deliberately, as step 4 of a documented measurement — *"Measure
under DB::listen — 21 queries for 10 posts (composer install + temp Pest probe,
since removed)"* — and it noted the tree stayed clean afterwards. For a
performance audit that must count real queries, that is correct behaviour, not
flailing.

The worktree removal may still be right for the *other* reason run 4 gave — an
agent that cannot run the suite it just wrote — and that is the claim the README
actually makes, so nothing there needs correcting. What does not survive is run
4's `composer install` attribution specifically: that stage would have appeared
with or without a worktree, because the fixture has no `vendor/` either way.

### 4. Three of five cases delegated nothing at all

`n-plus-one`, `action` and `hygiene` produced zero real subagent events: the
coordinator fast path (v1.15.0, single-specialist asks skip the pipeline) took
all three. `action` in particular went 1174s → 420s by not delegating.

That is the fast path working as designed, and it is most of this run's speed
improvement. Worth stating plainly because it also means **this run exercised the
multi-lane pipeline in only two cases** (`policy`, `tests`), so board-level
findings rest on a narrower base than "five cases" suggests.

## Baseline reseed

Reseeded from this run, per the run-4 policy of updating ceilings only after an
accepted run:

| Case | Was | Now | Why |
| --- | --- | --- | --- |
| `n-plus-one` | 200s | 250s | 178s here, creeping up across runs (96 → 157 → 178) |
| `policy` | 800s | 1100s | 994s twice; the 800s basis (run 2's 681s) no longer describes this case |
| `action` | 1200s | 600s | 420s without delegation; 1200s was set when it timed out |
| `tests` | 800s | 950s | 806s, and now correct — the 298s basis was a case that skipped the work |
| `hygiene` | 200s | 200s | 91s, unchanged |

**On raising `policy` to 1100s:** this accepts a 46% regression against the run-2
basis rather than fixing it, which is the trap ceilings exist to prevent. It is
recorded deliberately: two runs at exactly 994s is a stable cost, not a fluke, and
a ceiling that always reads REGRESSED stops carrying information. Finding 2 keeps
the actual driver on the record instead.

**On lowering `action` to 600s:** if the fast path stops taking that case, this
will read as a regression the first time it delegates again. That is the intended
signal, not a false alarm — but the basis note says so, so the next reader does
not simply raise it back.
